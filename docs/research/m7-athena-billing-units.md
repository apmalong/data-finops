# M7: the units of Athena's billed quantity (#310)

**Status:** research note (facts and options, not decisions). Sources checked **2026-11-18**. No AWS credentials and no AWS CLI were used. The repository evidence comes from files already on disk. Anything that no source states is marked *(inference)*. A source that is not AWS documentation, an AWS price list or an AWS staff answer is marked *(secondary)*, and no result depends on it.

## Question

The owner's Data Exports FOCUS 1.2 export bills Athena on-demand usage with `ConsumedUnit` `TB`. `providers/athena_billing.py` reads `TB` as 10^12 bytes (line 46). It rounds each query's `DataScannedInBytes` up to 10^6 bytes, with a minimum of 10 × 10^6 bytes (lines 42, 43, 70). On the demo lines of 2026-11-16 to 2026-11-18, the known Billable Usage divided by the billed quantity is 1.108 to 1.109 in these units. With MiB rounding and TiB, it is 1.010 to 1.011 (#310).

1. In Data Exports (FOCUS 1.2, CUR 2.0, legacy CUR), is Athena's usage quantity in 10^12 or 2^40 bytes? Which unit names appear, and does AWS define them?
2. In "rounded up to the nearest megabyte, with a 10 MB minimum per query", is MB 10^6 or 2^20 bytes? Is "per TB" decimal or binary?
3. Is `Statistics.DataScannedInBytes` the raw scan, and is it the billed quantity before the rounding?
4. Does any AWS source reconcile Athena billing with `DataScannedInBytes`? What convention does AWS billing document for other data sizes?
5. Does the repository's own real evidence fit decimal or binary units better?

## Findings

### 1. The unit of the billed quantity in Data Exports

- The FOCUS export and the price list use these names. The usage type is `USE1-DataScannedInTB` (PL-ATH, REPO-OQ line 9). The price list unit is `Terabytes`, and the price dimension reads "5.00 USD per Terabytes for DataScannedInTB in US East (N. Virginia)" (PL-ATH). The FOCUS export has `ConsumedUnit` and `PricingUnit` `TB`, and `ChargeDescription` repeats the price list text (REPO-OQ line 9, LOCAL-EXP).
- The price list product description reads "Charged for total data scanned per query with a minimum 10MB for each successful or cancelled queries" (PL-ATH). It gives no byte count for TB or MB.
- AWS's data dictionaries do not define a unit. `ConsumedUnit` is a "Provider-specified measurement unit indicating how a provider measures usage of a metered SKU" (DX-FOCUS). `pricing/unit` is "The pricing unit that AWS used for calculating your usage cost" (DX-CUR). `lineItem/UsageAmount` is "The amount of usage that you incurred during the specified time period" (DX-CUR).
- The FOCUS standard defines `TB` as 10^12 bytes and `TiB` as 2^40 bytes (FOCUS-UF, unit_format.md lines 33 to 51). But `ConsumedUnit` only "SHOULD conform to UnitFormat requirements" (FOCUS-UF, consumedunit.md). Thus a `TB` in a FOCUS column does not prove 10^12 bytes.
- AWS's own FOCUS export does not follow the decimal interpretation for S3 storage. AWS states that S3 storage is "calculated in binary gigabytes (GB), where 1 GB is 2^30 bytes" (S3-PR). The same export writes `GB-Months` as the `ConsumedUnit` of `TimedStorage-ByteHrs` for S3 (LOCAL-EXP). Thus AWS writes `GB` for a unit that it defines as binary *(inference: the two sources together)*.
- No AWS source found states the byte count of Athena's `TB` in Data Exports, CUR 2.0 or legacy CUR. This is **not documented**.
- Legacy CUR was not examined. Its `pricing/unit` for Athena is probably the price list's `Terabytes` *(inference)*.

### 2. The units of the pricing rule

- ATH-PR states: "You are charged for the number of bytes scanned per query, rounded up to the nearest megabyte, with a 10 MB minimum per query." For federated sources, queries "are billed per terabyte (TB) scanned ... rounded up to the nearest megabyte with a 10 megabyte minimum per query".
- ATH-PR's example uses whole terabytes only: "Price for 3 TB scanned is 3 * $5/TB = $15", and "Price for 0.25 TB = 0.25 * $5/TB = $1.25". It cannot tell decimal from binary.
- ATH-PR does not define MB or TB. This is **not documented**.
- Athena uses decimal MB for a different feature. The console control for data scanned per query takes "a value between 10 MB (minimum) and 7 EB (maximum)" (ATH-CTL). The API field `BytesScannedCutoffPerQuery` has a "Minimum value of 10000000" (ATH-WGC). Thus "10 MB" is 10^7 bytes in that control. This does not prove that billing uses the same MB *(inference)*.
- S3 states a binary convention for its storage, and says "1 TB is 2^40 bytes, i.e. 1024 GBs" (S3-PR). That statement covers S3 storage only. No AWS source found states one convention for all of AWS billing.

### 3. `DataScannedInBytes`

- ATH-QES: `DataScannedInBytes` is "The number of bytes in the data that was queried", of type Long. The CloudWatch metric `ProcessedBytes` is "The number of bytes that Athena scanned per DML query" (ATH-CW).
- The field is a byte count, not a unit with a prefix. Thus it is raw bytes (ATH-QES).
- No AWS source found states that it equals the billed quantity before the rounding and the minimum. This is **not documented**.
- The repository's real data does not fit "the billed bytes are `DataScannedInBytes`, rounded up, in decimal units". See [Evidence in this repository](#evidence-in-this-repository).

### 4. AWS reconciliation of Athena billing with query statistics

- No AWS documentation, AWS blog, Knowledge Center article or AWS staff answer was found that reconciles Athena's billed `DataScannedInTB` with `DataScannedInBytes`. Web searches on re:Post and AWS documentation gave no such page.
- The only re:Post answer found repeats the pricing rule without units, and an AI generated it (RP-1, *secondary*).
- Third-party blogs with conversion formulas came up in searches. They use 2^40 or 10^12 without a source. They are *secondary*, and this note does not use them.
- For the general convention: AWS documents binary GB and TB for S3 storage (S3-PR). Other services were not checked.

## Evidence in this repository

### The #25 and #91 observations: only the minimum

Every Athena usage line in the #25 and #91 deliveries is a whole number of minimum charges:

| Line (UTC) | `ConsumedQuantity` | Queries that billed | Source |
|---|---|---|---|
| 2026-11-01 21:00 to 22:00 | `0.00006` | six CTAS, 60 to 397 bytes each, all at 21:18 to 21:19 | REPO-OQ line 13, REPO-PR line 316, LOCAL-EXP |
| 2026-11-02 20:00 to 21:00 | `0.00002` | not known (history not kept), two minimums *(inference)* | REPO-OQ line 18, LOCAL-EXP |
| 2026-11-06 00:00 to 05:00 | `0.00003` | a CTAS (353 bytes), an INSERT (353 bytes), an OPTIMIZE (734 bytes), in three different hours | REPO-OQ line 20, LOCAL-EXP |

- In decimal units, each minimum is 10^7 bytes = 1 × 10^-5 TB. Six of them give `0.00006` exactly (REPO-OQ line 13).
- With a 10 MiB minimum and TiB, six minimums are 5.7220459 × 10^-5 TiB. Three in separate hours are 2.8610229 × 10^-5 TiB.
- The export keeps quantities to many places. Other lines in LOCAL-EXP read `0.0040997787` and `0.6666666672`. Thus a strict MiB and TiB calculation does not give `0.00006` without a coarse rounding step *(inference)*.
- These lines show only that one minimum is 1 × 10^-5 of the billed unit. They cannot show the size of that unit, because no query scanned more than the minimum.
- The #91 Coverage of 1 (REPO-PR lines 316, 317) therefore does not confirm decimal units for scans above the minimum. ADR 0017 line 26 and `athena_billing.py` line 11 say "decimal", but that rests on these lines only.

### The 2026-11-16 to 2026-11-18 demo lines

LOCAL-DB holds five versions of the demo workgroup's Athena usage lines, from several snapshots:

| Line (UTC) | `ConsumedQuantity` | `BilledCost` |
|---|---|---|
| 2026-11-16 04:00 to 19:00 | `0.00256` | 0.0128 |
| 2026-11-17 00:00 to 13:00 | `0.00182` | 0.0091 |
| 2026-11-17 00:00 to 19:00 | `0.002395` | 0.011975 |
| 2026-11-18 00:00 to 01:00 | `0.00067` | 0.00335 |
| 2026-11-18 00:00 to 07:00 | `0.001245` | 0.006225 |

- Two later versions differ from the earlier ones by the same six queries: one each of 11,400,896, 59,027,597, 74,752,338, 74,759,569, 169,589,644 and 244,349,213 bytes. The two differences are 0.002395 − 0.00182 and 0.001245 − 0.00067. Both are `0.000575` TB.
- These six queries scanned 633,879,257 bytes. Each is above the 10 MB minimum. The comparison for this one group is:

| Interpretation | Billable bytes | As a quantity | Against `0.000575` |
|---|---|---|---|
| Today: MB = 10^6, TB = 10^12 | 637 MB | 0.000637 TB | 1.108 |
| Raw bytes, TB = 10^12 | 633,879,257 | 0.000634 TB | 1.102 |
| Raw bytes, TB = 2^40 | 633,879,257 | 0.0005765 TiB | 1.0026 |
| MiB = 2^20, TB = 2^40 | 608 MiB | 0.0005798 TiB | 1.0084 |

- In decimal units, the bill is 575 × 10^6 bytes, which is 58.9 × 10^6 bytes less than the raw scan. An upward rounding cannot give less than the raw scan. Thus the decimal interpretation does not fit this group, whatever the rounding *(inference)*.
- In binary units, the bill is 632,219,186 bytes. That is 0.26 % below the raw scan and 0.84 % below the MiB-rounded scan. That fits within one step of 5 × 10^-6 TB *(inference)*.
- All eight Athena quantities seen (three in the table above the demo table, five in it) are whole multiples of 5 × 10^-6 of the billed unit. Thus each `BilledCost` is a multiple of $0.000025. A raw scan total in either unit rarely gives such a value *(inference)*. No source documents this step.

### A pattern that fits, not a result

Of 384 combinations tested (rounding unit, minimum, TB size, rounding step, rounding direction, and level of rounding), one combination fits all five demo lines and both checkable reference lines:

- each query is its raw `DataScannedInBytes` / 2^40, at least 1 × 10^-5 TB,
- queries are summed per UTC hour of completion,
- each hourly sum is rounded down to a multiple of 5 × 10^-6 TB.

This is a fit to few data, not a rule. The demo lines contain only three different hourly patterns (6, 13 and 22 queries). The choice between "rounded down" and "rounded to nearest" depends on one hour only (2026-11-16 04:00). The scripts are in the session scratchpad, not in the repository. No AWS source states this method.

## What is not known

- The byte count of `TB` in `USE1-DataScannedInTB`, in any Data Exports table. No AWS source states it.
- The byte count of "megabyte" and "10 MB" in Athena's pricing rule. Athena's workgroup control uses 10^7 bytes for "10 MB", but that is a different feature.
- Whether AWS applies the minimum as 10^7 bytes, 10 MiB, or 1 × 10^-5 of the billed unit.
- Whether AWS rounds each query, each hour or each line, and to what step. The 5 × 10^-6 step is observed, not documented.
- Whether `DataScannedInBytes` is exactly what Athena meters. The demo group bills less than its raw scan in decimal units, and 0.26 % less in binary units.
- Which hour a query near the end of an hour bills in (OQ-25).
- Whether CUR 2.0 or legacy CUR show the same quantities. Only FOCUS 1.2 was observed.
- AWS Support can answer the unit question for this account. This note did not ask.

## Consequence for #310

Facts:

- No primary source says that Athena's billed `TB` is 10^12 bytes. No primary source says that it is 2^40 bytes.
- AWS's FOCUS export writes decimal unit names for at least one binary unit (S3 storage, S3-PR with LOCAL-EXP).
- The demo data contradicts the decimal interpretation for queries above the minimum. It is close to the binary interpretation, within about 1 %.
- The reference data (minimums only) fits a minimum of 1 × 10^-5 of the billed unit. It does not fit a strict 10 MiB minimum in TiB.
- Billed quantities come in steps of 5 × 10^-6 TB. Thus a line with few queries cannot reconcile exactly under any per-query rule.

Options for the owner:

- **A.** Keep `athena-billable-usage/2` and the decimal units. The demo lines stay `coverage_exceeded`.
- **B.** A new policy version with `TB` = 2^40 bytes and MiB rounding. The demo lines have Coverage of about 1.01, which still exceeds 1.
- **C.** A new policy version with `TB` = 2^40 bytes, raw bytes, and a minimum of 1 × 10^-5 TB. The demo lines have Coverage of about 0.99 to 1.0. The pattern above is the only support for it.
  - *Correction (2026-11-18): that Coverage needs the hourly step of the pattern too. Without it, the demo lines come out at 1.0032 to 1.0038. With it, they come out at exactly 1. The owner chose the full pattern (Q165).*
- **D.** Any binary version together with a tolerance for the 5 × 10^-6 TB step in Coverage (ADR 0017). This changes how Coverage is compared, not only the units.
- **E.** Ask AWS Support for the units and the rounding before any change.

Each of B, C and D changes money logic (ADR 0017, `providers.athena_billing`). Earlier versions stay callable, so earlier Calculation Runs stay reproducible.
