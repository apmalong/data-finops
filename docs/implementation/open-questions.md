## From the pre-implementation architecture review (2026-11-01)
Context and evidence for each item: `docs/research/architecture-review.md`. Status is **open** until a decision is recorded here and applied to the authoritative document.

9. **Reconciliation unit.** Is each Billing Line partitioned exactly once (the pool only supplies weights), or is the Cost Pool the unit? (C3, P3) — **decided 2026-11-01:** each Billing Line is partitioned exactly once; the Cost Pool only supplies weights.
10. **Athena line with partial evidence.** When one Query Execution is the only *known* billable query in an aggregated Athena line, does it receive a metered share, or does the line stay Unallocated? Resolves the demo vs golden-oracle conflict. (C1, P7) — **decided 2026-11-01:** metered share only when query-history completeness for the line's scope is established; otherwise the unproven share is Unallocated. Golden scenario to be updated accordingly. Completeness is proven by comparing the line's billed usage quantity with known billable bytes: equal → whole line by bytes; fewer → known fraction by bytes, remainder Unallocated, Coverage recorded; more → whole line Unallocated and flagged.
11. **Attribution scope for MVP.** Are Allocations made only to workload leaves (Query Execution → Model Execution → Workload Run roll-up), with datasets, data products, tenants and downstream consumers deferred as separately reconciled views? (C8) — **decided 2026-11-01:** MVP allocates to workload leaves only, with roll-ups as sums; other targets deferred, to be recorded in an ADR.
12. **Canonical billing record.** Adopt FOCUS rows (column names, cost columns, ChargeCategory rows, `x_` extensions) as the internal billing record, and export-snapshot replacement as the revision model? (S1–S4, P1, P2) — **decided 2026-11-01:** FOCUS rows for one pinned release; revisions replace whole export snapshots per (billing account, billing period, source), prior snapshots retained.
13. **Quantization scale.** Quantize at each line's own decimal scale rather than currency minor units? (C4, P4) — **decided 2026-11-01:** quantize at the line's own scale (never coarser than the currency minor unit); largest remainder, stable target-ID tie-break; negatives by absolute value with sign restored.
14. **Category versus Confidence.** Is an Athena metered share category `direct` with confidence `metered_estimate`, and should `unallocated` be removed from the Confidence vocabulary? (C5) — **decided 2026-11-01:** metered share is category `direct`, confidence `metered_estimate`; `unallocated` removed from Confidence.
15. **Contract source of truth.** Code-first models generating the JSON Schemas (checked in CI), or schemas first? (C2, P9) — **decided 2026-11-01:** code-first Pydantic models generate the JSON Schemas; CI fails on drift; golden fixtures validate against them.
16. **Restatement and late telemetry.** Can an already-allocated period be recalculated indefinitely (new snapshot each time), or are periods closed after a cut-off? (C9) — **decided 2026-11-01:** any period may be recalculated; each Calculation Run yields a new snapshot with a current pointer and full history. Period close deferred.
17. **Default Cost Basis.** Which FOCUS cost column does the default Ledger view reconcile (for example BilledCost for invoice matching, or EffectiveCost for amortized showback)? Depends on 12. — **decided 2026-11-01:** every cost column reconciles independently; default view is BilledCost, EffectiveCost selectable.
18. **Credits and discounts.** Do credit and discount lines follow the usage they reduce (shared by the same weights), or stay Unallocated? Depends on 9 and 17. — **decided 2026-11-01:** in the MVP all Adjustment lines (credits, refunds, discounts) are Unallocated and shown as their own labelled amount; evidence-linked credit allocation is a later opt-in policy. Net-of-discount showback uses the EffectiveCost view.
19. **Failed and retried work.** Do charges for failed or retried executions go to that execution (shown with its status), or to Unallocated? Depends on 11. — **decided 2026-11-01:** charged to that execution and shown with its status; chargeability of failed queries is provider pricing in the versioned provider policy.

Recording (decided 2026-11-01): decisions 1 (narrowed), 9–10 and 11–12 become ADRs 0015–0017; 13–17 and 19 are applied directly to specs 02/03 and the schemas.
20. **Confidence for Idle amounts.** Confidence is required for direct and shared allocations and absent for Unallocated; what, if anything, does an Idle allocation carry? No MVP pool produces Idle (C12), so this can wait until capacity pricing. — open (non-blocking)
21. **FOCUS doubles to Decimal.** AWS Data Exports publishes FOCUS cost and quantity columns as `double`. Which conversion preserves the provider's stated amount (for example the shortest round-trip representation), and what scale does a line then have for quantization (decision 13)? Needed at M1. — **decided 2026-11-01:** convert each double through its shortest round-trip decimal representation (so 0.1 becomes `0.1`, not its binary expansion); that representation's scale is the line's own scale for quantization; retain the raw provider value in provenance; confirm against an anonymized real AWS FOCUS export before M1 closes.
22. **Athena queries dbt sends without a comment.** dbt-athena 1.11.1 drops the query comment from statements starting with `alter`, `drop`, `optimize`, `vacuum` or `msck` (`dbt/adapters/athena/query_headers.py`, found in #23), so those Query Executions cannot be linked to a Model Execution by comment. AWS states DDL is not billed, but OPTIMIZE and VACUUM on Iceberg tables scan data and are. How are they identified (for example by workgroup, timing within the invocation, or the dbt log), and until then do they count against Query-history Completeness for the line (decision 10)? Observe which ones the reference workload issues and whether they bill (#24, #25). Observed in #24: 3 of 20 queries uncommented, all `alter table` scanning 0 bytes. Athena also labels CTAS (`create table … as select`) `StatementType: DDL` although it scans data, so StatementType cannot decide billability. Needed by M2. — open
23. **dbt artifacts beyond their published schema.** dbt-core 1.12.6 writes fields and values that manifest v12 and run-results v6 do not list, without changing the schema version (#24). Should the checker and readers reject them or allow them? — **decided 2026-11-01:** allow additions: extra properties anywhere, and the one known value addition (`javascript` in `macro.dbt.materialization_function_default`'s `supported_languages`) only there; missing required fields, wrong types and other unknown values still fail. Each node type still has to match its own `resource_type`, except that dbt's two test types share one. OpenLineage stays strict. Applied in `scripts/verify_upstream.py` (#29).
