# Decisions requiring validation

1. Which real AWS CUR 2.0 / FOCUS export shape and cost basis should production ingestion support first? Test against anonymized samples. — **narrowed 2026-11-01:** AWS native FOCUS export (Data Exports) first, pinned to the FOCUS release AWS emits; CUR 2.0 via focus_converters deferred. Remaining: which release, and test against anonymized samples.
2. How will Athena query execution IDs be propagated through the chosen dbt Athena adapter and Airflow OpenLineage provider? Confirm actual hooks and query comments. — **dbt-athena half confirmed 2026-11-01** (#23, #24: a configured query comment carrying `node_id` and `invocation_id`, spec 04). M3 links the dbt invocation to its parent Airflow run through the ParentRunFacet using hand-written fixtures only; the Airflow provider's real output remains to be observed in a later reference workload extension, which does not block M3. — **Airflow half answered 2026-11-02 (#75, #76):** read from the pinned sources (#66): with Airflow 3.3.2 and its bundled OpenLineage provider 2.20.1, the parent run reaches dbt only when the DAG passes the provider's `lineage_parent_id` and `lineage_root_parent_id` macros to `dbt-ol` as `OPENLINEAGE_PARENT_ID` and `OPENLINEAGE_ROOT_PARENT_ID` (openlineage-dbt 1.54.0 also reads `OPENLINEAGE_CONTEXT`). Observed in the real run (#75, fixtures in `fixtures/reference-workload/airflow/`): dbt-ol's invocation run then carries a ParentRunFacet naming the Airflow task run as parent and the DAG run as root, with IDs matching Airflow's own events, and the product links invocation → dbt-ol run → task → DAG run. The invocation run takes Airflow's OpenLineage namespace instead of dbt-ol's default `dbt`; the model runs keep `dbt` (links never depend on namespaces). Observed offline (#74): `airflow dags test` omits the DAG run's START; the scheduler emits it. Airflow's events carry no Athena query execution IDs, so query correlation stays with the dbt query comment (M3). — **decided**
3. What provider-specific method will reconcile aggregated Athena billing to query-level metering, including minimum charges, discounts and adjustments? — partly decided by ADR 0017 (Coverage); the real billing shape is to be observed with the reference workload (ADR 0021). — **billing shape observed 2026-11-05 (#25)** in the real 2026-11 FOCUS 1.2 export. An anonymized copy is in `.local/focus-anon/2026-11/`; the anonymizer hashes free text, so `ChargeDescription` was read from the raw export.
   - **Granularity:** one `Usage` line per usage account, region, workgroup and UTC hour (`ChargePeriodStart` to `ChargePeriodEnd` is one hour), with `ChargeFrequency` `Usage-Based`.
   - **Columns:**
     - `ServiceName` is `Amazon Athena`; `x_Operation` is `PRESTO_QUERY` (engine 3).
     - `SkuMeter` is `USE1-DataScannedInTB`, and `ChargeDescription` reads "5.00 USD per Terabytes for DataScannedInTB in US East (N. Virginia)".
     - `ListUnitPrice` is 5.0.
     - `ConsumedUnit` and `PricingUnit` are both `TB`, and `ConsumedQuantity` equals `PricingQuantity`.
     - `ResourceId` is the workgroup ARN (`arn:aws:athena:<region>:<account>:workgroup/<name>`).
   - **Billed quantity:** decimal, as `athena-billable-usage/1` assumes. The reference run's line for 2026-11-01 21:00 reads 6e-05 TB, with BilledCost and EffectiveCost both $0.0003. All 20 of the run's queries completed between 21:18:59 and 21:19:55 UTC. Of those, the six CTAS statements (Athena labels them `DDL`) scanned 60 to 397 bytes each; at the 10 MB minimum each, they come to 6 × 10^7 bytes = 6e-05 TB, exactly. The other 14 scanned 0 bytes and billed nothing: nine DDL (CREATE TABLE, CREATE VIEW, ALTER TABLE) and five DML (four SELECT, one INSERT). That contradicts the policy for 0-byte DML; see OQ-24.
   - **Free Tier credit:** a separate `Credit` line in the same hour with the same SKU. It has no `ResourceId`, a null `ConsumedQuantity`, a `PricingQuantity` of 0, `ChargeFrequency` `One-Time`, and BilledCost and EffectiveCost equal and opposite to the usage line's. It is an Adjustment (OQ-18), never metered.
   - **Tax:** one monthly `Tax` line for product code AmazonAthena at 0.00, with no `ResourceId`.
   - **Checked against ADR 0017:**
     - Each usage line names its workgroup and hour, so its billing scope (ADR 0023) holds exactly the queries billed in it. With 0-byte queries free, the reference line would have Query-history Completeness. Under `athena-billable-usage/1` it does not (OQ-24).
     - A second line, 2026-11-02 20:00, reads 2e-05 TB, which at the minimum is two queries (inferred). It comes from a run whose Athena history was not kept. With no known queries, its Coverage is 0 and it stays Unallocated `coverage_remainder`, as designed.
   - **Checked in #91 (2026-11-07)** against the 2026-11-07 21:20 delivery and the reference workgroup's history, saved before the teardown (#26):
     - **Probes**, one kind per UTC hour on 2026-11-06: a SELECT (0 bytes), the same SELECT reused (0 bytes), a CTAS on Iceberg (353 bytes, labelled `DDL`), an INSERT (353 bytes), an OPTIMIZE (734 bytes, labelled `DDL`), a VACUUM (0 bytes), a failed SELECT and a DROP. One usage line, 00:00 to 05:00, reads 3e-05 TB: 10 MB each for the CTAS, the INSERT and the OPTIMIZE. The 0-byte SELECT, the reused result, the VACUUM, the failed query and the DROP billed nothing: the delivery reaches 2026-11-07 14:00 for other services, and no Athena line follows 05:00 on 2026-11-06.
     - **Lines can span several hours:** that line's charge period is five hours, though the probes ran in separate hours. Scope already uses the whole period. `athena-billing-scope/2` keys the pool label by the line's charge period rather than its day.
     - **Coverage**, computed by `data-finops calculate` on the real delivery and history under `athena-billable-usage/2`: 1 for the 2026-11-01 21:00 line (six CTAS) and for the 2026-11-06 line (CTAS, INSERT, OPTIMIZE). The 2026-11-02 20:00 line stays Unallocated: see OQ-25.
     - **Rows per workgroup:** each line's ResourceId names the workgroup, but only one workgroup ran, so a split between two workgroups in one hour is inferred, not observed.
     - **Not observed:** a reused result of a query that scanned data. The probes for it (#91's `9-select-scan`, `10-select-scan-reused`) never started. AWS documents that a reused result scans no data, so `/2` bills it nothing either way; that is documentation, not an observation.

## From the pre-implementation architecture review (2026-11-01)
Context and evidence for each item: `docs/research/architecture-review.md`. Status is **open** until a decision is recorded here and applied to the authoritative document.

9. **Reconciliation unit.** Is each Billing Line partitioned exactly once (the pool only supplies weights), or is the Cost Pool the unit? (C3, P3) — **decided 2026-11-01:** each Billing Line is partitioned exactly once; the Cost Pool only supplies weights.
10. **Athena line with partial evidence.** When one Query Execution is the only *known* billable query in an aggregated Athena line, does it receive a metered share, or does the line stay Unallocated? Resolves the demo vs golden-oracle conflict. (C1, P7) — **decided 2026-11-01:** metered share only when query-history completeness for the line's scope is established; otherwise the unproven share is Unallocated. Golden scenario to be updated accordingly. Completeness is proven by comparing the line's billed usage quantity with known billable bytes: equal → whole line by bytes; fewer → known fraction by bytes, remainder Unallocated, Coverage recorded; more → whole line Unallocated and flagged.
11. **Attribution scope for MVP.** Are Allocations made only to workload leaves (Query Execution → Model Execution → Workload Run roll-up), with datasets, data products, tenants and downstream consumers deferred as separately reconciled views? (C8) — **decided 2026-11-01:** MVP allocates to workload leaves only, with roll-ups as sums; other targets deferred, to be recorded in an ADR.
12. **Canonical billing record.** Adopt FOCUS rows (column names, cost columns, ChargeCategory rows, `x_` extensions) as the internal billing record, and export-snapshot replacement as the revision model? (S1–S4, P1, P2) — **decided 2026-11-01:** FOCUS rows for one pinned release; revisions replace whole export snapshots per (billing account, billing period, source), prior snapshots retained.
13. **Quantization scale.** Quantize at each line's own decimal scale rather than currency minor units? (C4, P4) — **decided 2026-11-01:** quantize at the line's own scale (never coarser than the currency minor unit); largest remainder, stable target-ID tie-break; negatives by absolute value with sign restored.
14. **Category versus Confidence.** Is an Athena metered share category `direct` with confidence `metered_estimate`, and should `unallocated` be removed from the Confidence vocabulary? (C5) — **decided 2026-11-01:** metered share is category `direct`, confidence `metered_estimate`; `unallocated` removed from Confidence.
15. **Contract source of truth.** Code-first models generating the JSON Schemas (checked in CI), or schemas first? (C2, P9) — **decided 2026-11-01:** code-first Pydantic models generate the JSON Schemas; CI fails on drift; golden fixtures validate against them.
16. **Restatement and late telemetry.** Can an already-allocated period be recalculated indefinitely (new snapshot each time), or are periods closed after a cut-off? (C9) — **decided 2026-11-01:** any period may be recalculated; each Calculation Run yields a new snapshot with a current pointer and full history. Period close deferred.
17. **Default Cost Basis.** Which FOCUS cost column does the default Ledger view reconcile (for example BilledCost for invoice matching, or EffectiveCost for amortized showback)? Depends on 12. — **decided 2026-11-01:** every cost column reconciles independently; default view is BilledCost, EffectiveCost selectable.
18. **Credits and discounts.** Do credit and discount lines follow the usage they reduce (shared by the same weights), or stay Unallocated? Depends on 9 and 17. — **decided 2026-11-01:** in the MVP all Adjustment lines (credits, refunds, discounts) are Unallocated and shown as their own labelled amount; evidence-linked credit allocation is a later opt-in policy. Net-of-discount showback uses the EffectiveCost view.
19. **Failed and retried work.** Do charges for failed or retried executions go to that execution (shown with its status), or to Unallocated? Depends on 11. — **decided 2026-11-01:** charged to that execution and shown with its status; chargeability of failed queries is provider pricing in the versioned provider policy.

Recording (decided 2026-11-01): decisions 1 (narrowed), 9–10 and 11–12 become ADRs 0015–0017; 13–17 and 19 are applied directly to specs 02/03 and the schemas.
20. **Confidence for Idle amounts.** Confidence is required for direct and shared allocations and absent for Unallocated; what, if anything, does an Idle allocation carry? No MVP pool produces Idle (C12), so this can wait until capacity pricing. — open (non-blocking)
21. **FOCUS doubles to Decimal.** AWS Data Exports publishes FOCUS cost and quantity columns as `double`. Which conversion preserves the provider's stated amount (for example the shortest round-trip representation), and what scale does a line then have for quantization (decision 13)? Needed at M1. — **decided 2026-11-01:** convert each double through its shortest round-trip decimal representation (so 0.1 becomes `0.1`, not its binary expansion); that representation's scale is the line's own scale for quantization; retain the raw provider value in provenance; confirm against an anonymized real AWS FOCUS export before M1 closes. — **confirmed 2026-11-05 (#12)** against the real 2026-10 and 2026-11 deliveries. Of 91,091 doubles, none needs more than 15 significant digits, and their shortest forms have 1 to 12 decimal places. Every Billing Line reconciles with zero delta for BilledCost and EffectiveCost (progress.md, M1). No discrepancy found.
22. **Athena queries dbt sends without a comment.** dbt-athena 1.11.1 drops the query comment from statements starting with `alter`, `drop`, `optimize`, `vacuum` or `msck` (`dbt/adapters/athena/query_headers.py`, found in #23), so those Query Executions cannot be linked to a Model Execution by comment. AWS states DDL is not billed, but OPTIMIZE and VACUUM on Iceberg tables scan data and are. How are they identified (for example by workgroup, timing within the invocation, or the dbt log), and until then do they count against Query-history Completeness for the line (decision 10)? Observe which ones the reference workload issues and whether they bill (#24, #25). Observed in #24: 3 of 20 queries uncommented, all `alter table` scanning 0 bytes. Athena also labels CTAS (`create table … as select`) `StatementType: DDL` although it scans data, so StatementType cannot decide billability. Needed by M3 (moved from M2 on 2026-11-01: M2 stores queries' workload context but does not correlate them). — **M3 half decided 2026-11-01:** uncommented queries are stored as Query Executions with Link Outcome `no_evidence`; nothing is inferred from workgroup, timing or the dbt log (ADR 0006). Whether they count against Query-history Completeness moves to M4, where Coverage is computed. — **M4 half decided 2026-11-02:** they count toward Coverage by billing scope, linked or not (ADR 0023); their Billable Usage comes from the Athena policy, where a `DDL` statement scanning 0 bytes (the observed `alter table`) is 0 and anything that scanned data, OPTIMIZE and VACUUM included, bills its rounded scan (spec 03, M4 structure 8). Whether OPTIMIZE and VACUUM really bill is checked against the real export (#25). — **observed 2026-11-07 (#91):** an OPTIMIZE that scanned 734 bytes billed the 10 MB minimum; a VACUUM that scanned 0 bytes billed nothing. — **decided**
23. **dbt artifacts beyond their published schema.** dbt-core 1.12.6 writes fields and values that manifest v12 and run-results v6 do not list, without changing the schema version (#24). Should the checker and readers reject them or allow them? — **decided 2026-11-01:** allow additions: extra properties anywhere, and the one known value addition (`javascript` in `macro.dbt.materialization_function_default`'s `supported_languages`) only there; missing required fields, wrong types and other unknown values still fail. Each node type still has to match its own `resource_type`, except that dbt's two test types share one. OpenLineage stays strict. Applied in `scripts/verify_upstream.py` (#29).
24. **Zero-byte DML is free.** `athena-billable-usage/1` exempts only DDL that scanned 0 bytes and charges every other succeeded query at least 10 MB. The real export (#25, OQ-3) shows four SELECTs and one INSERT that scanned 0 bytes and billed nothing. Under the policy, the reference line's known Billable Usage would be 1.1e-04 TB against 6e-05 TB billed: Coverage of about 1.83, so the whole line would go Unallocated and flagged (ADR 0017). Proposal for #91: a new policy version, `athena-billable-usage/2`, in which any query that scanned 0 bytes bills nothing, whatever its statement type. `/1` stays as it is, so earlier Calculation Runs stay reproducible. — **decided 2026-11-07 (#91):** the probes confirmed it (a 0-byte SELECT, a reused result and a VACUUM billed nothing), and `/2` is the current version. Under it, the reference line's Coverage is 1.
25. **The billed hour can be later than completion.** In the real export (#91), the reference run of 2026-11-02 had two queries that scanned data (60 and 397 bytes) and completed at 19:59:46 and 19:59:56 UTC. Their 2 × 10 MB were billed in the line for 20:00 to 21:00, not 19:00 to 20:00. `athena-billing-scope` scopes by completion time, so that line keeps Coverage 0 and stays Unallocated as `coverage_remainder`. Nothing is misallocated, but the line is not metered. Which timestamp does Athena bill by, and how late can it be? One boundary case is too few to choose a tolerance: observe queries that complete in the last minute of an hour before changing the scope. — open
