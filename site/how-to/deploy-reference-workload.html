Deploy the reference workload

On this page

  • What it deploys and costs
  • Configure the stack
  • Deploy
  • Run the workload and collect its outputs
  • Tear it down

The reference workload is a small Athena, dbt and Airflow pipeline in a real AWS account. It produces a real bill, real Athena history and real OpenLineage events, to check data-finops against more than the hand-written fixtures (ADR 0021). This guide deploys it with Pulumi, runs it and tears it down. The full steps are in the reference workload's README.

Not run on this page. It creates resources in a real AWS account and costs real money. The owner approves every pulumi preview, pulumi up, workload run and pulumi destroy against a real account.

What it deploys and costs

The Pulumi program creates, in us-east-1:

  • an S3 bucket, with public access blocked and encryption on;
  • a Glue database, reference_workload;
  • an Athena workgroup, data-finops-reference, that writes its results to the bucket;
  • optionally, an AWS Budget that alerts by email.

The costs are small. The tiny models cost a fraction of a cent per run, and the S3 and Glue costs are negligible. Two settings bound them: the workgroup's per-query scan cutoff, and the optional Budget. The Budget is account-wide, and it alerts when forecast or actual spend reaches its amount.

Configure the stack

Use a dedicated AWS profile with least privilege. From the repository root:

cd examples/reference-workload
uv sync
export PULUMI_BACKEND_URL="file://$(cd ../.. && pwd)/.local/pulumi"
export PULUMI_CONFIG_PASSPHRASE="<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your profile>
pulumi config set bytesScannedCutoffPerQuery 104857600
pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
cd examples/reference-workload
uv sync
$env:PULUMI_BACKEND_URL = "file://$((Resolve-Path ../..).Path)/.local/pulumi"
$env:PULUMI_CONFIG_PASSPHRASE = "<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your profile>
pulumi config set bytesScannedCutoffPerQuery 104857600
pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
  • PULUMI_BACKEND_URL keeps the Pulumi state in the git-ignored .local/pulumi. The program refuses any backend that is not file://.
  • bytesScannedCutoffPerQuery is the most an Athena query may scan, in bytes. The default is 100 MiB, and the least is 10 MiB.
  • budgetMonthlyUsd and budgetEmail go together. Leave both unset for no Budget.
  • pulumi stack init dev is needed only the first time.

Deploy

pulumi preview
pulumi up
pulumi preview
pulumi up

The stack's outputs are the bucket, the database and the workgroup. The workload's runs need the bucket.

Run the workload and collect its outputs

The README gives the steps for dbt, run from WSL or Linux with dbt-ol, and for Airflow, run with Docker Compose. Their OpenLineage events land in the git-ignored .local/openlineage/. Before anything leaves your machine, anonymize the outputs with the secret described in Exit codes and environment:

export DATA_FINOPS_ANON_SECRET="<long random value>"
uv run python scripts/anonymize_focus_export.py <downloaded-export-dir> <output-dir>
uv run python scripts/anonymize_workload_outputs.py <outputs-dir> <output-dir>
$env:DATA_FINOPS_ANON_SECRET = "<long random value>"
uv run python scripts/anonymize_focus_export.py <downloaded-export-dir> <output-dir>
uv run python scripts/anonymize_workload_outputs.py <outputs-dir> <output-dir>

Run these from the repository root. The output must be outside the repository or under .local/. The published sample is in fixtures/reference-workload/.

Tear it down

pulumi destroy
pulumi destroy

This removes the bucket, with everything in it, the Glue database, the workgroup and the Budget. What pulumi destroy does not remove:

  • the local state in .local/pulumi and the outputs in .local/openlineage/;
  • the WSL virtual environment, .venv-linux.

The recorded teardown, and how to recreate the stack, are tracked in issue #26.
