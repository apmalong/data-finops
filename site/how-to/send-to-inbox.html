Send workload metadata to the Inbox

On this page

  • What goes where
  • Give the producer access
  • Write OpenLineage events
  • Write dbt artifacts
  • Collect from your machine

A Deployment does not receive OpenLineage events or dbt artifacts over HTTP. Producers write files to its Inbox, a prefix in the Deployment's bucket, and the next Collection Run pulls them (ADR 0027). This guide writes both kinds of file, then runs a Collection Run from your machine with data-finops collect.

The commands on this page use your own AWS profile and a real bucket, so they are not run when the site is checked. In each command, replace example-deployment-bucket with your Deployment's bucket.

What goes where

  • inbox/openlineage/: OpenLineage event files, one event per file or JSON Lines. Each event is capped at 1 MiB, as on every other path.
  • inbox/dbt/<invocation>/: one dbt invocation's manifest.json and run_results.json. A folder is collected once both files are there. Until then, each Collection Run reports it as waiting.

Every file is capped at 512 MiB. A larger file is rejected by its key and never downloaded.

Give the producer access

The identity that writes needs only s3:PutObject on inbox/*. The stack outputs producerPolicyArn, a managed policy that grants exactly that. Attach it to the role your Airflow or dbt runs as, for example:

aws iam attach-role-policy --role-name <producer role> --policy-arn <producerPolicyArn> --profile <admin profile>
aws iam attach-role-policy --role-name <producer role> --policy-arn <producerPolicyArn> --profile <admin profile>

The producer cannot read, list or delete what is in the Inbox. The bucket is the bucket output. Both outputs are listed by pulumi stack output; see Deploy to AWS.

Write OpenLineage events

Have the OpenLineage client write events to local files with its file transport, for example in openlineage.yml:

transport:
  type: file
  log_file_path: lineage/events

The file transport writes one file per event, each a single line of JSON, which data-finops reads as JSON Lines. Leave debug_mode off: it writes indented JSON that data-finops refuses. After the run, copy the files to the Inbox:

aws s3 sync lineage/ s3://example-deployment-bucket/inbox/openlineage/
aws s3 sync lineage/ s3://example-deployment-bucket/inbox/openlineage/

The file transport can also write to an s3:// path directly through fsspec, which needs the s3fs package installed beside the client. That set-up has not been verified with data-finops.

Write dbt artifacts

After each dbt run or dbt build, copy the two artifacts into a folder named after the invocation. The folder name is your choice; data-finops reads the invocation from the files themselves:

aws s3 cp target/manifest.json s3://example-deployment-bucket/inbox/dbt/inv-001/manifest.json
aws s3 cp target/run_results.json s3://example-deployment-bucket/inbox/dbt/inv-001/run_results.json
aws s3 cp target/manifest.json s3://example-deployment-bucket/inbox/dbt/inv-001/manifest.json
aws s3 cp target/run_results.json s3://example-deployment-bucket/inbox/dbt/inv-001/run_results.json

Collect from your machine

A Deployment runs a Collection Run every day, and its collector can be invoked to run one now (Deploy to AWS). To run one from your own machine instead, read-only against AWS, install the aws extra and write a settings file, for example collect.toml:

uv sync --extra aws --frozen
uv sync --extra aws --frozen
bucket = "example-deployment-bucket"
region = "us-east-1"
account_id = "123456789012"
workgroups = ["example-workgroup"]
export_bucket = "example-export-bucket"
export_prefix = "focus"
export_name = "example-focus-1-2"
profile = "your-profile"

account_id and workgroups name the Athena workgroups whose query history is collected too; see Ingest Athena query history. The three export_ settings name the FOCUS export, as configured in Data Exports; see Ingest a FOCUS export. profile is optional. An unknown setting is refused, so a typo never does nothing quietly. Then collect into a database:

data-finops collect --db finops.sqlite --config collect.toml
data-finops collect --db finops.sqlite --config collect.toml

collect prints one line of JSON, the Collection Run's summary: for each source, how many items were stored, how many were duplicates and which were rejected, then any warnings and the Calculation Runs it started. Each rejected item follows on its own line, by key, and by position within the file for one event:

{"sources":{"dbt":{"stored":2,…},"openlineage":{"stored":4,…,"rejected":[{"item":"inbox/openlineage/run.json#2",…}]}},"warnings":[],"calculation_run_ids":["calc-…"],"exit_code":1}
  inbox/openlineage/run.json#2: invalid RunEvent: run/runId (format)

An OpenLineage JobEvent or DatasetEvent, which data-finops does not read, is listed under warnings by key and position. It does not change the exit code. A dbt folder still missing one of its files is listed there too, until the file arrives. A file already collected is never fetched again, unless a producer overwrites it with new content. A rejected file is not retried. The exit code is 0, 1 when something was rejected, or 2 when a source could not be read. See Exit codes and environment.
