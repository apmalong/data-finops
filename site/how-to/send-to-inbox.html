    Send workload metadata to the Inbox

    On this page

    • What goes where
    • Give the producer access
    • Write OpenLineage events
    • Write dbt artifacts
    • Collect from your machine

    A Deployment does not receive OpenLineage events or dbt artifacts over HTTP. Producers write files to its Inbox, a prefix in the Deployment's bucket, and the next Collection Run pulls them (ADR 0027). This guide writes both kinds of file, then runs a Collection Run from your machine with data-finops collect.

    Not run on this page. These commands use your own AWS profile and a real bucket.

    In each command, replace example-deployment-bucket with your Deployment's bucket.

    What goes where

    • inbox/openlineage/: OpenLineage event files, one event per file or JSON Lines. Each event is capped at 1 MiB, as on every other path.
    • inbox/dbt/<invocation>/: one dbt invocation's manifest.json and run_results.json. A folder is collected when both files are in it. Until then, each Collection Run shows the warning <folder>/: waiting for <files>.

    Every file is capped at 512 MiB. A larger file is rejected by its key and never downloaded.

    Give the producer access

    The identity that writes requires s3:PutObject on inbox/*. If kmsKeyArn is set, it also requires kms:GenerateDataKey on that key. The stack outputs producerPolicyArn, a managed policy that grants these permissions and no others. Attach it to the role your Airflow or dbt runs as, for example:

    aws iam attach-role-policy --role-name <producer role> --policy-arn <producerPolicyArn> --profile <admin profile>
    aws iam attach-role-policy --role-name <producer role> --policy-arn <producerPolicyArn> --profile <admin profile>

    The producer cannot read, list or delete what is in the Inbox. The bucket is the bucket output. pulumi stack output lists both outputs. See Deploy to AWS.

    Write OpenLineage events

    Have the OpenLineage client write events to local files with its file transport, for example in openlineage.yml:

    transport:
  type: file
  log_file_path: lineage/events

    The file transport writes one file per event, each a single line of JSON, which data-finops reads as JSON Lines. Leave debug_mode off: it writes indented JSON that data-finops refuses. After the run, copy the files to the Inbox:

    aws s3 sync lineage/ s3://example-deployment-bucket/inbox/openlineage/
    aws s3 sync lineage/ s3://example-deployment-bucket/inbox/openlineage/

    The file transport can also write to an s3:// path directly through fsspec, which requires the s3fs package installed beside the client. That set-up has not been verified with data-finops.

    Write dbt artifacts

    After each dbt run or dbt build, copy the two artifacts into a folder named after the invocation. You choose the folder name. data-finops reads the invocation from the files:

    aws s3 cp target/manifest.json s3://example-deployment-bucket/inbox/dbt/inv-001/manifest.json
aws s3 cp target/run_results.json s3://example-deployment-bucket/inbox/dbt/inv-001/run_results.json
    aws s3 cp target/manifest.json s3://example-deployment-bucket/inbox/dbt/inv-001/manifest.json
aws s3 cp target/run_results.json s3://example-deployment-bucket/inbox/dbt/inv-001/run_results.json

    Collect from your machine

    A Deployment runs a Collection Run every day, and its collector can be invoked to run one now (Deploy to AWS). To run one from your own machine instead, read-only against AWS, install the aws extra and write a settings file, for example collect.toml:

    uv sync --extra aws --frozen
    uv sync --extra aws --frozen
    bucket = "example-deployment-bucket"
region = "us-east-1"
account_id = "123456789012"
workgroups = ["example-workgroup"]
export_bucket = "example-export-bucket"
export_prefix = "focus"
export_name = "example-focus-1-2"
profile = "your-profile"

    account_id and workgroups name the Athena workgroups. The run also collects the query history of these workgroups. See Ingest Athena query history. The three export_ settings name the FOCUS export, as it is configured in Data Exports. See Ingest a FOCUS export.

    profile is optional. So is inbox_retention_days. It is the number of days after which S3 expires an Inbox object. With it, the run warns about an object that it did not collect before S3 expires it. data-finops refuses an unknown setting. Thus a typo never fails silently. Then collect into a database:

    data-finops collect --db finops.sqlite --config collect.toml
    data-finops collect --db finops.sqlite --config collect.toml

    collect prints one line of JSON: the summary of the Collection Run. For each source, the summary gives the number of stored items, the number of duplicates and the rejected items. Then it gives the warnings and the Calculation Runs that it started. Each rejected item follows on its own line, by key. For one event, the line also gives the position of the event in the file:

    {"sources":{"dbt":{"stored":2,…},"openlineage":{"stored":4,…,"rejected":[{"item":"inbox/openlineage/run.json#2",…}]}},"warnings":[],"calculation_run_ids":["calc-…"],"exit_code":1}
  inbox/openlineage/run.json#2: invalid RunEvent: run/runId (format)

    An OpenLineage JobEvent or DatasetEvent, which data-finops does not read, is listed under warnings by key and position. It does not change the exit code. A dbt folder that does not have both of its files yet is also in that list, until the file arrives. A file that was collected is never fetched again, unless a producer overwrites it with new content. A rejected file is not retried.

    In a Deployment, Inbox objects expire after inboxRetentionDays (default 30), and the collector gets this setting. In its last 7 days, an object that was not collected is listed under warnings, with its key, its age and the days left. With a retention shorter than 7 days, each such object is listed:

    inbox/openlineage/run.json: not collected, 25 days old, expires in 5 days

    To keep the data, correct a rejected file and write it to the Inbox again. For a dbt folder, send the file that it waits for. Do this before the object expires.

    The exit code is 0, 1 when something was rejected, or 2 when a source could not be read. See Exit codes and environment.
