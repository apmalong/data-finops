Deploy to AWS

On this page

  • Before you start
  • Build the package
  • Configure the stack
  • Check it with the policy pack
  • Deploy
  • Run a first Collection Run

A Deployment runs data-finops in one AWS account: a collector function that runs a Collection Run once a day, and a read-only API behind an IAM-authorized Function URL (ADR 0026). This guide builds the functions' package, configures the Pulumi stack, checks it with the policy pack, deploys it and runs a first Collection Run. Deployment architecture explains what it creates and what it costs.

Owner-run: not run on this page. Every command here reaches a real AWS account, and the deploy creates resources that cost money. Only the account owner runs pulumi preview, pulumi up and pulumi destroy against a real account.

The owner can follow this page by hand, or run it as one wizard: deploy-and-verify.sh. It runs every step below, checks what a destroy would keep, can validate the IAM policies with IAM Access Analyzer, and runs and reads back a first Collection Run. It asks before every step that changes anything, and masks account IDs, buckets, profiles and the API's URL in everything it shows and records. From the repository root:

bash infra/pulumi/aws/wizards/deploy-and-verify.sh
& "C:\Program Files\Git\bin\bash.exe" infra/pulumi/aws/wizards/deploy-and-verify.sh

On Windows it needs Git Bash, not WSL's bash. Its masked record is written to .local/.

Before you start

  • One AWS account holds the FOCUS export's bucket, the Athena workgroups and the Deployment. Reading another account's export or history is not supported.
  • The FOCUS export uses the "create new" delivery mode, as Ingest a FOCUS export describes. A Collection Run refuses an export that overwrites its files. An export encrypted with a KMS key is not supported yet.
  • The database fits in a function's /tmp. The stack leaves it at Lambda's default, 512 MB, which both functions share with the package's own files.
  • An AWS profile for a dedicated deployer identity, created by the account owner. The stack never creates it. A draft least-privilege policy for it is iam/deployer-policy.draft.json. It is unvalidated: the wizard can check it with IAM Access Analyzer, and a missing permission shows up as an access error in pulumi up.
  • The Pulumi CLI, version 3.272.0, and uv. A test checks the installed CLI is that release.

Build the package

Both functions run from one zip built from your checkout. From the repository root:

cd infra/pulumi/aws
uv sync --frozen
uv run python -m deployment.package
cd infra/pulumi/aws
uv sync --frozen
uv run python -m deployment.package

This writes build/data-finops-lambda.zip, about 66 MB, after downloading the arm64 wheels from PyPI. pulumi up refuses to run without it. Build it again after every change to the checkout: a changed zip redeploys both functions.

Configure the stack

Still in infra/pulumi/aws:

mkdir -p ../../../.local/pulumi
export PULUMI_BACKEND_URL="file://$(cd ../../.. && pwd)/.local/pulumi"
export PULUMI_CONFIG_PASSPHRASE="<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your deployer profile>
pulumi config set aws:region <region>
pulumi config set exportBucket <export bucket>
pulumi config set exportName <export name>
pulumi config set exportPrefix <export prefix>
pulumi config set --path 'workgroups[0]' <workgroup>
New-Item -ItemType Directory -Force ../../../.local/pulumi | Out-Null
$env:PULUMI_BACKEND_URL = "file://$((Resolve-Path ../../..).Path.Replace('\', '/'))/.local/pulumi"
$env:PULUMI_CONFIG_PASSPHRASE = "<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your deployer profile>
pulumi config set aws:region <region>
pulumi config set exportBucket <export bucket>
pulumi config set exportName <export name>
pulumi config set exportPrefix <export prefix>
pulumi config set --path 'workgroups[0]' <workgroup>
  • PULUMI_BACKEND_URL keeps the stack's state in the repository's git-ignored .local/pulumi, which must exist first. The program refuses any backend that is not file://.
  • pulumi stack init dev is needed only the first time.
  • Leave out exportPrefix when the export has no S3 path prefix.
  • Add a second workgroup as workgroups[1], and so on.

Every other setting has a default. Two are worth setting now: a Budget alert, and an alarm for a failing collector. The Budget is account-wide: it alerts on the whole account's forecast and actual spend, not only the Deployment's.

pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
pulumi config set alarmEmail <your email>
pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
pulumi config set alarmEmail <your email>

Once the stack is up, AWS emails alarmEmail a link to confirm its subscription to the alarm's topic. The alarm's emails start only after it is followed. Every setting, its default and its bounds are in Deployment settings. The stack checks them all before it declares anything.

Check it with the policy pack

The policy pack holds the Deployment's mandatory rules: a private, encrypted, versioned, TLS-only bucket; an IAM-only Function URL; bounded and logged functions; least-privilege IAM; no VPC or database servers; a Budget that alerts on forecast and actual spend. It has its own environment:

cd policy
uv sync --frozen
cd ..
pulumi preview --policy-pack policy
cd policy
uv sync --frozen
cd ..
pulumi preview --policy-pack policy

A violation fails the preview and names the policy and the resource. At a real preview, a policy document computed from other resources' ARNs is not known yet, so its checks are only advisory there. CI enforces them on every pull request, over the stack's mocked state.

Deploy

pulumi up --policy-pack policy
pulumi up --policy-pack policy

Read the plan before you confirm it. The bucket and everything on it are kept when the stack is destroyed, unless deleteDataOnDestroy says otherwise: see Tear down a Deployment. Then list the stack's outputs:

pulumi stack output
pulumi stack output

Each output is described in Deployment settings. The next steps need collectorFunction and apiUrl.

Run a first Collection Run

The schedule starts the first run at its next time, 06:00 UTC by default. To run one now, invoke the collector. It ignores the event it is sent:

aws lambda invoke --function-name <collectorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> collector-result.json
aws lambda invoke --function-name <collectorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> collector-result.json

collector-result.json then holds the Collection Run's summary: for each source, what was stored, duplicated or rejected, any warnings, and the Calculation Run it started. The same summary is one line in the collector's log:

aws logs tail /aws/lambda/<collectorFunction> --since 1h --region <region> --profile <your profile>
aws logs tail /aws/lambda/<collectorFunction> --since 1h --region <region> --profile <your profile>

A run that could not read a source, or that lost a write to a concurrent run, ends as an error. The schedule invokes the collector asynchronously, so Lambda retries a failed run up to twice. Every run starts again from the current database, and replaying what was already stored changes nothing. To read what it collected, see Read a Deployment. To send it OpenLineage events and dbt artifacts, see Send workload metadata to the Inbox.
