    Deploy to AWS

    On this page

    • Before you start
    • Build the package
    • Configure the stack
    • Check it with the policy pack
    • Deploy
    • Run a first Collection Run
    • Read the phase timings
    • Add the Public Demo (optional)

    A Deployment runs data-finops in one AWS account (ADR 0026). It has a collector function that runs a Collection Run one time each day. It also has a read-only API behind an API Gateway HTTP API that IAM authorizes. This guide builds the functions' package, configures the Pulumi stack, checks it with the policy pack, deploys it and runs a first Collection Run. Deployment architecture explains what it creates and what it costs.

    Owner-run: not run on this page. Every command here reaches a real AWS account, and the deploy creates resources that cost money. Only the account owner runs pulumi preview, pulumi up and pulumi destroy against a real account.

    The owner can follow this page by hand, or run it as one wizard: deploy-and-verify.sh. The wizard does these things:

    • It runs each step below.
    • It checks what a destroy would keep.
    • It can validate the IAM policies with IAM Access Analyzer.
    • It runs a first Collection Run and reads its result.
    • It can read the phase timings of the runs that it started.
    • It can add the Public Demo. Then the wizard deploys the demo, writes the demo's dataset, runs the Simulated Orchestrator one time and opens demoUrl.
    • It asks before each step that changes something.
    • It masks account IDs, buckets, profiles and the URL of the API in all that it shows and records.

    From the root of the repository, run the wizard:

    bash infra/pulumi/aws/wizards/deploy-and-verify.sh
    & "C:\Program Files\Git\bin\bash.exe" infra/pulumi/aws/wizards/deploy-and-verify.sh

    On Windows, it requires Git Bash, not the bash of WSL. Its masked record is written to .local/.

    Before you start

    • One AWS account holds the FOCUS export's bucket, the Athena workgroups and the Deployment. data-finops does not support the export or the history of a different account.
    • The FOCUS export uses the "create new" delivery mode, as Ingest a FOCUS export describes. A Collection Run refuses an export that overwrites its files. An export encrypted with a KMS key is not supported yet.
    • The database fits in a function's /tmp. The ephemeralStorageMb setting gives the collector, the API and the publisher 10,240 MB by default. The database and the Inbox file that a run collects share this space.
    • An AWS profile for a dedicated deployer identity, created by the account owner. The stack never creates it. A draft least-privilege policy for it is iam/deployer-policy.draft.json. It is not validated. The wizard can check it with IAM Access Analyzer. If the policy does not have a permission, pulumi up shows an access error.
    • The Pulumi CLI, version 3.272.0, and uv. A test checks the installed CLI is that release.

    Build the package

    Both functions run from one zip built from your checkout. From the repository root:

    cd infra/pulumi/aws
uv sync --frozen
uv run python -m deployment.package
    cd infra/pulumi/aws
uv sync --frozen
uv run python -m deployment.package

    This command downloads the arm64 wheels from PyPI. Then it writes build/data-finops-lambda.zip, about 66 MB. The versions are the versions in uv.lock. pulumi up refuses to run without the zip. After each change to the checkout, build the zip again. A changed zip deploys each function again.

    Configure the stack

    Still in infra/pulumi/aws:

    mkdir -p ../../../.local/pulumi
export PULUMI_BACKEND_URL="file://$(cd ../../.. && pwd)/.local/pulumi"
export PULUMI_CONFIG_PASSPHRASE="<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your deployer profile>
pulumi config set aws:region <region>
pulumi config set exportBucket <export bucket>
pulumi config set exportName <export name>
pulumi config set exportPrefix <export prefix>
pulumi config set --path 'workgroups[0]' <workgroup>
    New-Item -ItemType Directory -Force ../../../.local/pulumi | Out-Null
$env:PULUMI_BACKEND_URL = "file://$((Resolve-Path ../../..).Path.Replace('\', '/'))/.local/pulumi"
$env:PULUMI_CONFIG_PASSPHRASE = "<choose one; needed for every later command>"
pulumi stack init dev
pulumi config set aws:profile <your deployer profile>
pulumi config set aws:region <region>
pulumi config set exportBucket <export bucket>
pulumi config set exportName <export name>
pulumi config set exportPrefix <export prefix>
pulumi config set --path 'workgroups[0]' <workgroup>
    • PULUMI_BACKEND_URL keeps the stack's state in the repository's git-ignored .local/pulumi, which must exist first. The program refuses any backend that is not file://.
    • pulumi stack init dev is necessary only the first time.
    • Leave out exportPrefix when the export has no S3 path prefix.
    • Add a second workgroup as workgroups[1], and so on.

    Each other setting has a default. We recommend that you set two of them now: a Budget alert, and an alarm for when the collector fails. The Budget is for the whole account. It sends an alert about the forecast spend and the actual spend of the whole account, not only of the Deployment.

    pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
pulumi config set alarmEmail <your email>
    pulumi config set budgetMonthlyUsd <amount>
pulumi config set budgetEmail <your email>
pulumi config set alarmEmail <your email>

    Once the stack is up, AWS emails alarmEmail a link to confirm its subscription to the alarm's topic. The alarm's emails start only after it is followed. Every setting, its default and its bounds are in Deployment settings. The stack checks them all before it declares anything.

    Check it with the policy pack

    The policy pack holds the mandatory rules of the Deployment:

    • a private, encrypted, versioned bucket that accepts only TLS
    • an API whose routes accept only IAM authorization, with rate limits
    • functions with limits and logs
    • least-privilege IAM
    • no VPC and no database servers
    • a Budget that sends alerts about forecast spend and actual spend

    The policy pack has its own environment:

    cd policy
uv sync --frozen
cd ..
pulumi preview --policy-pack policy
    cd policy
uv sync --frozen
cd ..
pulumi preview --policy-pack policy

    A violation fails the preview and names the policy and the resource. At a real preview, a policy document computed from other resources' ARNs is not known yet, so its checks are only advisory there. CI enforces them on every pull request, over the stack's mocked state.

    Deploy

    pulumi up --policy-pack policy
    pulumi up --policy-pack policy

    Read the plan before you confirm it. The bucket and everything on it are kept when the stack is destroyed, unless deleteDataOnDestroy says otherwise: see Tear down a Deployment. Then list the stack's outputs:

    pulumi stack output
    pulumi stack output

    Each output is described in Deployment settings. The next steps require collectorFunction and apiUrl.

    Run a first Collection Run

    The schedule starts the first run at its next time, 06:00 UTC by default. To run one now, invoke the collector. It ignores the event it is sent:

    aws lambda invoke --function-name <collectorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> collector-result.json
    aws lambda invoke --function-name <collectorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> collector-result.json

    collector-result.json then holds the Collection Run's summary: for each source, what was stored, duplicated or rejected, any warnings, and the Calculation Run it started. The same summary is one line in the collector's log:

    aws logs tail /aws/lambda/<collectorFunction> --since 1h --region <region> --profile <your profile>
    aws logs tail /aws/lambda/<collectorFunction> --since 1h --region <region> --profile <your profile>

    A run that could not read a source, or that lost a write to a concurrent run, ends as an error. The schedule invokes the collector asynchronously, so Lambda retries a failed run up to twice. Each run starts again from the current database. If a run reads data that is already stored, nothing changes. To read what it collected, see Read a Deployment. To send it OpenLineage events and dbt artifacts, see Send workload metadata to the Inbox.

    Read the phase timings

    Each run of the collector and of the publisher logs one line for each phase of the run (ADR 0033). A line gives the seconds that the phase took and the peak memory of the function so far, in MiB:

    {"event": "phase", "function": "collector", "phase": "calculate", "seconds": 1.852, "peak_mb": 180}

    The collector logs the phases fetch, ingest, calculate and write. The publisher logs download, open, parse, render and write. To read the lines of the collector:

    aws logs filter-log-events --log-group-name /aws/lambda/<collectorFunction> --filter-pattern '{ $.event = phase }' --query 'events[*].[message]' --output text --region <region> --profile <your profile>
    aws logs filter-log-events --log-group-name /aws/lambda/<collectorFunction> --filter-pattern '{ $.event = phase }' --query 'events[*].[message]' --output text --region <region> --profile <your profile>

    For the publisher, use the output demoPublisherFunction in place of collectorFunction. The deploy wizard has a stage that reads both.

    Add the Public Demo (optional)

    The owner of data-finops runs the Public Demo in a Deployment. You do not need it to use data-finops. It adds a public site on CloudFront and an Athena workgroup with a generated dataset. It also adds a scheduled function that runs real queries in that workgroup. Those queries cost about $1 to $2 a month. The site publishes only the demo workgroup's lines, never the rest of the bill.

    In infra/pulumi/aws, turn the demo on and give it the demo's Cost Dimensions, then deploy again:

    pulumi config set publicDemo true
pulumi config set costDimensions ../../../examples/public-demo/cost-dimensions.toml
pulumi up --policy-pack policy
    pulumi config set publicDemo true
pulumi config set costDimensions ../../../examples/public-demo/cost-dimensions.toml
pulumi up --policy-pack policy

    examples/public-demo/cost-dimensions.toml groups cost by the team, the tenant and the Airflow run ID that the Simulated Orchestrator writes in each query comment. As in Airflow, the run ID is the scheduled time, so all the DAGs of one start have the same value. See Configure Cost Dimensions. The settings demoSchedule and demoScanCutoffBytes have defaults, which Deployment settings gives. The stack adds the demo workgroup to the workgroups whose history the collector reads.

    Write the demo dataset one time. The generator writes some hundred MB of Parquet, and takes some minutes:

    aws lambda invoke --function-name <demoGeneratorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> generator-result.json
    aws lambda invoke --function-name <demoGeneratorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> generator-result.json

    If you invoke it again, it writes the same files. Then run the Simulated Orchestrator one time, so that you do not wait for its schedule. It runs the DAGs that are due now:

    aws lambda invoke --function-name <demoSimulatorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> simulator-result.json
    aws lambda invoke --function-name <demoSimulatorFunction> --cli-read-timeout 900 --region <region> --profile <your profile> simulator-result.json

    The bill of these queries arrives in the FOCUS export some hours later. After the next Collection Run, the publisher writes the first Demo Snapshot. Then open demoUrl. Until the first snapshot, the demo shows nothing.

    To stop the demo, set publicDemo to false and run pulumi up. This deletes the demo's bucket and everything in it, because all of it can be made again. To stop only the queries, disable the simulator's schedule in EventBridge Scheduler.
