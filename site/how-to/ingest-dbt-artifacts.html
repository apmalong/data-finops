Ingest dbt artifacts

On this page

  • Load the manifest and the run results
  • Load them again
  • If an artifact is rejected
  • Let Query Executions name their Model Execution

A dbt invocation writes manifest.json and run_results.json to its target/ directory. The manifest gives the dbt Nodes, and the run results give the Model Executions. This guide loads both.

Load the manifest and the run results

Load each artifact with its own command, in either order:

data-finops ingest dbt fixtures/dbt/manifest.json --db finops.sqlite
data-finops ingest dbt fixtures/dbt/run_results.json --db finops.sqlite
dbt: stored inv-001
dbt: stored inv-001

Each line names the dbt invocation the artifact belongs to. Copy the artifacts out of target/ after each invocation, because the next one overwrites them.

Load them again

data-finops ingest dbt fixtures/dbt/manifest.json --db finops.sqlite
dbt: duplicate inv-001

An artifact already stored with the same content stores nothing. Another artifact of the same kind for the same invocation prints changed_copy, and is kept beside the first.

If an artifact is rejected

A file that is not a dbt manifest or run results prints dbt: rejected: with the reason, such as not a dbt artifact. Nothing from it is stored, and the command exits with 1.

Let Query Executions name their Model Execution

dbt artifacts do not name the Athena Query Executions a Model Execution issued. To link them, configure dbt to send a Trusted Query Comment with the invocation_id and node_id of each dbt Node it runs. dbt's default query comment has no invocation_id. The configuration is in the reference workload's README. Then ingest the Athena history.
