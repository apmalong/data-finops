    Configure Cost Dimensions

    On this page

    • Write the file
    • Send the values from dbt
    • Ingest with the file
    • Read the totals of each value
    • In a Deployment

    A Cost Dimension groups cost by an attribute that your organization selects, for example a team or a tenant. You declare each dimension and where its value comes from in one TOML file. Each Calculation Run then records the value and its source on each Allocation. This guide writes the file, sends the values from dbt, calculates with the file and reads the totals of each value. The decision is ADR 0031, and the rules are in spec 09.

    A dimension is a view of the Allocations. It does not change how a Billing Line is split. Its value is a claim: it tells you what a query comment, a tag or a map says. It is never Evidence for an Identity Link.

    Write the file

    This guide uses fixtures/docs/cost-dimensions.toml:

    [dimensions.team]
sources = ["query_comment.team", "workgroup_map"]
workgroup_map = { "demo" = "analytics" }

[dimensions.environment]
sources = ["query_comment.target_name"]
    [dimensions.team]
sources = ["query_comment.team", "workgroup_map"]
workgroup_map = { "demo" = "analytics" }

[dimensions.environment]
sources = ["query_comment.target_name"]

    Each table under dimensions is one dimension. Its sources are tried in order, and the first source that gives a value wins. There are three kinds of source:

    • query_comment.<key>: a key in the JSON comment on the first line of the query, the same comment that holds the Trusted Query Comment.
    • openlineage_tag.<key>: a tag in the OpenLineage tags facets (of the run and of its job) of the Workload Run of the query's dbt invocation. The tags of that run come first, then the tags of its parents, up to the root run. If one run has two values for the key, that run is skipped, and its parents are tried.
    • workgroup_map: the Athena workgroup of the query, through the map that the dimension gives. For an amount with no query, it is the workgroup of the Billing Line.

    The rules:

    • A file has 8 dimensions at most, and its query_comment sources name 16 keys at most.
    • Ingest keeps only the comment keys that the file names. A value longer than 128 characters is removed, and the ingest result counts it as a dropped claim.
    • An unknown key or source refuses the file. The error names the file and the fault, never a value.
    • Add sensitive = true to a dimension to keep its values out of the minimal Cost Explanation and out of the public demo. The full API still shows them.

    Send the values from dbt

    dbt sends a comment on the first line of each query that it runs. Make that comment JSON, with the Trusted Query Comment's invocation_id and node_id, and with each key that your dimensions read. Put this macro in macros/data_finops_query_comment.sql of your dbt project:

    {% macro data_finops_query_comment(node) -%}
  {%- set comment = {
      "app": "dbt",
      "dbt_version": dbt_version,
      "invocation_id": invocation_id,
      "node_id": node.unique_id if node is not none else none,
      "target_name": target.name,
      "team": node.config.meta.get("team") if node is not none else none,
  } -%}
  {{- return(tojson(comment)) -}}
{%- endmacro %}
    {% macro data_finops_query_comment(node) -%}
  {%- set comment = {
      "app": "dbt",
      "dbt_version": dbt_version,
      "invocation_id": invocation_id,
      "node_id": node.unique_id if node is not none else none,
      "target_name": target.name,
      "team": node.config.meta.get("team") if node is not none else none,
  } -%}
  {{- return(tojson(comment)) -}}
{%- endmacro %}

    Then select it in dbt_project.yml. The comment must be at the start of the query, so do not append it:

    query-comment:
  comment: "{{ data_finops_query_comment(node) }}"
  append: false
    query-comment:
  comment: "{{ data_finops_query_comment(node) }}"
  append: false

    This macro reads the team from each model's meta, for example {{ config(meta={"team": "finance"}) }}. You can also read a value from an environment variable that your orchestrator sets, with env_var("TEAM", ""). The reference workload uses the same macro without team: see its README. The macro writes the same comment for each query of a model, so each query of the model gets the same claims.

    Ingest with the file

    Give the same file to ingest athena and to calculate. Ingest keeps the claims, and the Calculation Run resolves them:

    data-finops ingest focus fixtures/focus/export-2026-10.json --db finops.sqlite
data-finops ingest athena fixtures/athena/query-executions.json --account-id 123456789012 --region us-east-1 --dimensions fixtures/docs/cost-dimensions.toml --db finops.sqlite
data-finops calculate --dimensions fixtures/docs/cost-dimensions.toml --db finops.sqlite
data-finops serve --db finops.sqlite
    data-finops ingest focus fixtures/focus/export-2026-10.json --db finops.sqlite
data-finops ingest athena fixtures/athena/query-executions.json --account-id 123456789012 --region us-east-1 --dimensions fixtures/docs/cost-dimensions.toml --db finops.sqlite
data-finops calculate --dimensions fixtures/docs/cost-dimensions.toml --db finops.sqlite
data-finops serve --db finops.sqlite
    focus: new aws-focus-123456789012-2026-10-v1
athena: 2 accepted, 0 duplicates, 0 changed copies, 0 rejected
calculate: 123456789012 2026-10-01 aws-data-exports:FOCUS_1_2_AWS: new calc-…
serving finops.sqlite at http://127.0.0.1:8000/ (Ctrl+C to stop)

    serve does not stop, so run the next command in a second terminal.

    The configuration applies only from now on:

    • A comment key that you add later applies only to the queries that are ingested after it. The query text is not kept, so the key cannot be read again from stored queries.
    • A changed file does not change a stored Allocation Snapshot, and it does not start a new snapshot by itself. It applies at the next snapshot that new inputs make. Each snapshot records the SHA-256 of the file that it used.

    Read the totals of each value

    Ask for the Roll-ups of one dimension:

    curl -s http://127.0.0.1:8000/v1/rollups/dimensions/team
    curl.exe -s http://127.0.0.1:8000/v1/rollups/dimensions/team
    {"calculation_run_id":"calc-…","dimension":"team","totals":[{"currency":"USD","cost_basis":"BilledCost","amount":"10.00"},…"items":[{"value":"analytics","totals":[{"currency":"USD","cost_basis":"BilledCost","amount":"6.00","sources":[{"source":"workgroup_map","amount":"6.00"}]},…{"value":null,"totals":[{"currency":"USD","cost_basis":"BilledCost","amount":"4.00","sources":[{"source":null,"amount":"4.00"}]},…

    Read it in this order:

    • totals is the total of the Allocation Snapshot for each currency and Cost Basis: $10.00 BilledCost. The values always add up to it, so you do not have to add them.
    • analytics has $6.00. The fixture's comments have no team key, so the second source gave the value: the query ran in the demo workgroup, which the map gives to analytics.
    • The value null is unassigned: $4.00. It is the S3 line, which has no query and no workgroup. Unassigned cost stays visible. It is never spread among the other values.

    A dimension that no Allocation of the snapshot has gives 404. The dashboard shows the same totals in its Cost Dimensions section, with a list to select the dimension.

    In a Deployment

    Set the stack's costDimensions setting to the path of your file, then run pulumi up. The stack uploads the file to config/cost-dimensions.toml in the Deployment's bucket, and only the collector can read it. The collector reads it at the start of each Collection Run. If it cannot read or use the file, the run stops, and the error names the key of the object, never its content. See Deployment settings.

    data-finops collect takes a --dimensions file, or the key of the object in its settings (cost_dimensions_key), but not both.
