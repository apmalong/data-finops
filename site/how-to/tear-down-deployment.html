    Tear down a Deployment

    On this page

    • Before you destroy
    • Destroy and keep the data
    • Destroy and delete the data
    • What is left

    pulumi destroy removes a Deployment. By default it keeps the bucket, with the database and the Inbox in it, so a mistaken destroy loses no data. This guide removes a Deployment either way and lists what is left behind.

    Owner-run: not run on this page. Every command here reaches a real AWS account, and the deploy creates resources that cost money. Only the account owner runs pulumi preview, pulumi up and pulumi destroy against a real account.

    The owner can follow this page by hand, or run it as one wizard: teardown.sh. The wizard does these things:

    • It runs each step below.
    • It also tears down the reference workload.
    • It checks that the state of each stack is empty.
    • It checks that the main resources are gone in AWS. These are the functions, the producer and reader policies, and the bucket if you chose to delete it. They also include the bucket, Glue database, workgroup and Budget of the reference workload.
    • It asks before each step that changes something.
    • It masks account IDs, buckets, profiles and the URL of the API in all that it shows and records.

    From the root of the repository, run the wizard:

    bash infra/pulumi/aws/wizards/teardown.sh
    & "C:\Program Files\Git\bin\bash.exe" infra/pulumi/aws/wizards/teardown.sh

    On Windows, it requires Git Bash, not the bash of WSL. Its masked record is written to .local/.

    Before you destroy

    Detach the producer and reader policies from every identity they were attached to. IAM refuses to delete a managed policy that is still attached, and the destroy stops there:

    aws iam list-entities-for-policy --policy-arn <producerPolicyArn> --profile <admin profile>
aws iam list-entities-for-policy --policy-arn <readerPolicyArn> --profile <admin profile>
aws iam detach-role-policy --role-name <role> --policy-arn <policy arn> --profile <admin profile>
    aws iam list-entities-for-policy --policy-arn <producerPolicyArn> --profile <admin profile>
aws iam list-entities-for-policy --policy-arn <readerPolicyArn> --profile <admin profile>
aws iam detach-role-policy --role-name <role> --policy-arn <policy arn> --profile <admin profile>

    Run every command below from infra/pulumi/aws, with PULUMI_BACKEND_URL and PULUMI_CONFIG_PASSPHRASE set as in Deploy to AWS.

    Destroy and keep the data

    pulumi destroy
    pulumi destroy

    This command deletes the functions, their log groups and roles, the schedule and the Function URL. It also deletes the producer and reader policies, the alarm and its topic, the Budget, and the Lambda package object. S3 Versioning keeps the last version of the package, about 66 MB, until it expires after noncurrentVersionDays. The command keeps the bucket and each setting on it: the public access blocks, encryption, versioning, the expiry rules and the TLS-only policy. The bucket leaves the state of the stack. Thus a later pulumi up tries to create a new bucket with a new name, and does not adopt this bucket.

    While the bucket is kept, AWS bills its storage, and its expiry rules continue to operate. Inbox objects expire after inboxRetentionDays, and old object versions expire after noncurrentVersionDays. To delete the bucket later, empty it in the S3 console, which deletes each version. Then delete the bucket.

    Destroy and delete the data

    To delete the bucket with everything in it, every version included, change the setting and apply it first. The stack records whether to keep the bucket when it is deployed, not when it is destroyed:

    pulumi config set deleteDataOnDestroy true
pulumi up
pulumi destroy
    pulumi config set deleteDataOnDestroy true
pulumi up
pulumi destroy

    This cannot be undone. If you think that you will want the database later, download it first. See Read a Deployment.

    What is left

    • The stack's local state, in .local/pulumi. Remove the empty stack with pulumi stack rm dev.
    • The package, infra/pulumi/aws/build/data-finops-lambda.zip, which is git-ignored.
    • The deployer identity and its profile, which the owner created and removes.
    • Anything a producer or reader set up on its own side, such as an OpenLineage configuration that writes to the Inbox.
    • The FOCUS export and the Athena workgroups, which the Deployment only read.

    The reference workload is a separate stack with its own teardown: see Deploy the reference workload.
