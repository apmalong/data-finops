Export Snapshots and restatements

Providers publish a Billing Period's bill more than once, as charges settle and credits arrive. This page explains how data-finops keeps every publication, and which one it uses. The decisions are in ADR 0015, ADR 0019 and ADR 0020, with the calculation side in spec 03. They stay authoritative. To do it, see Handle a restated export.

The whole Export Snapshot is the unit

An Export Snapshot is every Billing Line of one Snapshot Scope (a billing account, a Billing Period and a source), as the provider published it at one time. A restatement replaces the whole Export Snapshot. data-finops never patches single Billing Lines, because a provider's restatement can change, add or remove any of them.

Within an Export Snapshot, rows are never deduplicated. Two identical rows are two Billing Lines, each identified by its snapshot and position. Merging them would drop money the provider billed, and the Ledger's totals would no longer equal the provider's.

Stored Export Snapshots never change

Each load has one of three outcomes:

  • New: new content is stored. It is reported as new if it is now current, or as superseded if a later publication is current.
  • Replay: content equal to the current Export Snapshot, or an ID already stored with the same content, stores nothing.
  • Rejected: an ID already stored with different content is refused, because what was stored is never rewritten.

The latest publication is current

For each Snapshot Scope, the current Export Snapshot is the one the provider published last, with ties broken by the higher ID. It never depends on the order you load them in, so a late-arriving earlier publication cannot take over. The publication time comes only from the provider's own metadata. For an AWS Data Exports Delivery, that is the creation time in the manifest's data folder, never a file time or the time of loading.

Earlier publications become Superseded Snapshots. They are kept as history.

Allocations follow, and keep their history

A Calculation Run allocates the current Export Snapshot of each Snapshot Scope. After a restatement, the next run makes a new Allocation Snapshot, and the earlier one is kept, not overwritten. Its provenance shows that it is no longer current and which run superseded it. The API still serves it when asked for by its Calculation Run ID, so a figure reported last week can always be explained as it was then.

A Calculation Run whose inputs equal the current Allocation Snapshot's stores nothing. Inputs equal to a superseded one's make a new Allocation Snapshot, so going back to an earlier state is recorded too.
