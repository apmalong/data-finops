Deployment architecture

On this page

  • Two functions and one bucket
  • Pulled, not pushed
  • Trust boundaries
  • What it costs
  • Limits to watch

A Deployment runs data-finops in one AWS account, with no servers to keep running and no network to manage. This page explains its parts, where its trust boundaries are and what it costs. The decisions are in ADR 0026, ADR 0027 and ADR 0028, with the design in spec 08. They stay authoritative.

Two functions and one bucket

data-finops keeps everything in one SQLite file, written by one writer at a time. A Deployment keeps that design rather than adding a database server:

  • The database is one S3 object, database/data-finops.sqlite, in the Deployment's private bucket.
  • The collector is the only writer. Once a day it downloads the object, runs one Collection Run and uploads the result, only if the object is still the one it downloaded (an S3 conditional write on its ETag). A concurrent write makes the upload fail instead of being lost, and the next run starts again from the current object.
  • The API only reads. It serves the object the last run wrote, never a half-written one, and downloads it again only when its ETag changes.

Neither function runs in a VPC, so there is no NAT gateway, subnet or endpoint to pay for or secure. Both reach S3, Athena and CloudWatch through AWS's public endpoints, signed with their own roles.

Pulled, not pushed

Locally, OpenLineage events can arrive over HTTP with a bearer token. A Deployment has no such endpoint. A long-lived shared token on a public URL is the risk the token was kept local to avoid, and stock OpenLineage clients cannot sign requests for an IAM-authorized URL. Producers write files to the Inbox instead, with an IAM policy that allows nothing else, and the next Collection Run pulls what is new. Lineage therefore arrives once a day, which is when costs are calculated anyway. See Send workload metadata to the Inbox.

Trust boundaries

  • The account. The FOCUS export, the Athena workgroups and the Deployment are in one account. Nothing crosses into another.
  • The Function URL. It is reachable from the internet, but AWS rejects every request not signed by a principal with the reader policy before the function runs. The API mounts only the read endpoints: there is no write route to reach.
  • Producers. A producer can put objects in the Inbox and do nothing else: not read them back, list them or touch the database. What it writes is screened like any input: each event capped at 1 MiB, each file at 512 MiB, and a rejected file reported by its key and reason, never its content.
  • The collector's reach. It reads the export, the Athena history of the configured workgroups and the Inbox, and writes only the database object. It cannot run queries or read their results, which an explicit deny enforces. Query text is dropped before anything is stored.
  • The bucket. Public access is blocked, ACLs are disabled, requests without TLS are denied, and objects are encrypted with an S3-managed key or, optionally, a customer-managed KMS key. Versioning keeps earlier databases for noncurrentVersionDays.
  • What readers see. A Cost Explanation shows the minimal Billing Line by default, withholding tags and free-text names, because a Deployment's readers may be a wider group than its billing administrators.

The policy pack checks these rules on every pull request. Each function's role is limited to the actions its job needs, and the pack fails a role granted anything more. The local rules are in Security model.

What it costs

At the expected scale, a few thousand to about a million Billing Lines a month, a Deployment costs under $1 a month in us-east-1. These are estimates from AWS's published prices, checked on 2026-11-06, not measurements:

  • The estimates assume a daily run of 60 seconds at 1 GB of memory (small) to 300 seconds at 2 GB, 10,000 API requests a month, and a database of 0.1 GB to 12 GB.
  • Without Lambda's free tier, add about $0.16 (small) or $0.37 a month.
  • A customer-managed KMS key adds $1 a month.

AWS has no hard spending cap, and a Budget cannot stop a function. A Deployment bounds its cost instead: every function has a timeout and a memory size, the schedule runs once a day with at most two retries, logs expire, Inbox objects and old database versions expire, and the optional Budget emails on forecast and actual spend. If something still goes wrong, the API can be switched off at once: see Read a Deployment.

Limits to watch

  • Each Collection Run moves the whole database in and out of S3. As it grows, so do the run's time and the API's cold start.
  • A function's /tmp holds at most 10,240 MB, and one upload at most 5 GB, so the database must stay under both.
  • Athena keeps query history for 45 days. A Deployment that stops collecting for longer loses the gap, and the summary warns when it may have.
  • None of these is measured on a large account yet. Each is a revisit trigger in ADR 0026 or spec 08.
