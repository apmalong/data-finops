    Identity Links and Evidence

    On this page

    • Only explicit Evidence links
    • The Trusted Query Comment
    • Link Outcomes
    • Stored as reported, never merged
    • The cost of no Identity Link

    A Roll-up says which Model Execution or Workload Run an Allocation adds up to. It is only as good as the link behind it. This page explains what counts as Evidence for an Identity Link, and what happens when there is none. The decisions are in ADR 0006 and ADR 0022, with details in spec 03 and spec 04. They stay authoritative.

    Only explicit Evidence links

    An Identity Link connects the records of one piece of work in different systems. These records are a Query Execution in the history of Athena, the Model Execution in dbt's run results, and the Workload Runs in OpenLineage events. It requires explicit Evidence: an exact provider ID, or metadata from a trusted source. Time overlap is never Evidence. A Query Execution that overlaps a dbt run can belong to any work.

    The Trusted Query Comment

    dbt artifacts do not name the Athena Query Executions a Model Execution issued. The Evidence comes from Athena's side instead. dbt can send a query comment before each statement, and data-finops trusts it only at the very start of the query text. That Trusted Query Comment names the dbt invocation and node. Only those two values are kept. The rest of the query text is dropped.

    • dbt's default comment has no invocation_id, so it must be configured. The configuration is in the reference workload's README.
    • dbt-athena sends statements that start with alter, drop, optimize, vacuum or msck without the comment, so those have no Identity Link.

    An OpenLineage run from dbt-ol links to its Model Execution by the dbt node and invocation it reports. Workload Runs link to their parents and roots as the events name them.

    Link Outcomes

    Each claim a Query Execution makes has a Link Outcome:

    • linked: the claim names a known Model Execution. This is an Identity Link.
    • no_evidence: there is no Trusted Query Comment.
    • unmatched: the comment names a dbt node and invocation that no run results report.
    • ambiguous: there is more than one candidate, for example, reports of one Query Execution that name different Model Executions. No Identity Link is made.

    Links are worked out when they are asked for, from what is stored, so the order the inputs arrive in never changes them. In the tutorial, q-004's reports disagree, so its Link Outcome is ambiguous, and model.demo.customers, which only q-004 claims, gets no Roll-up.

    The Link Outcome no_evidence is not the Unallocated reason no_evidence. Always say which one you mean.

    Stored as reported, never merged

    OpenLineage runs are stored exactly as each event reported them. They are linked, never merged into one record. A report that is different from an earlier report is kept next to it, as a separate observation. Thus no report silently replaces another. Two reports of one Query Execution that name different Model Executions also get a flag. A Model Execution comes only from dbt's run results, never from an OpenLineage event alone.

    The cost of no Identity Link

    If there is no Identity Link, the money still goes to the same place. A Query Execution without one still gets its share of the Billing Line, because billing scope is accounting, not Evidence (ADR 0023). It only has no Roll-up to a Model Execution or Workload Run. Thus a broken comment configuration shows as Allocations that roll up to nothing. It does not show as Allocations given to the wrong Model Execution.
