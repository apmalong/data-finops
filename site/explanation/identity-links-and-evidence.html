Identity Links and Evidence

A Roll-up says which dbt model or Airflow run a cost belongs to. It is only as good as the link behind it. This page explains what counts as Evidence for an Identity Link, and what happens when there is none. The decisions are in ADR 0006 and ADR 0022, with details in spec 03 and spec 04. They stay authoritative.

Only explicit Evidence links

An Identity Link connects records of one piece of work as different systems saw it: a Query Execution in Athena's history, the Model Execution in dbt's run results, and the Workload Runs in OpenLineage events. It needs explicit Evidence: an exact provider ID, or metadata from a trusted source. Running at the same time is never Evidence. A Query Execution that overlaps a dbt run may belong to anything.

The Trusted Query Comment

dbt artifacts do not name the Athena Query Executions a Model Execution issued. The Evidence comes from Athena's side instead. dbt can send a query comment before each statement, and data-finops trusts it only at the very start of the query text. That Trusted Query Comment names the dbt invocation and node. Only those two values are kept. The rest of the query text is dropped.

  • dbt's default comment has no invocation_id, so it must be configured. The configuration is in the reference workload's README.
  • dbt-athena sends statements starting with alter, drop, optimize, vacuum or msck without the comment, so those have no Identity Link.

An OpenLineage run from dbt-ol links to its Model Execution by the dbt node and invocation it reports. Workload Runs link to their parents and roots as the events name them.

Link Outcomes

Each claim a Query Execution makes has a Link Outcome:

  • linked: the claim names a known Model Execution. This is an Identity Link.
  • no_evidence: there is no Trusted Query Comment.
  • unmatched: the comment names a dbt node and invocation that no run results report.
  • ambiguous: there is more than one candidate, such as reports of one Query Execution naming different Model Executions. No Identity Link is made.

Links are worked out when they are asked for, from what is stored, so the order the inputs arrive in never changes them. In the tutorial, q-004's reports disagree, so its Link Outcome is ambiguous, and model.demo.customers, which only q-004 claims, gets no Roll-up.

The Link Outcome no_evidence is not the Unallocated reason no_evidence. Always say which one you mean.

Stored as reported, never merged

OpenLineage runs are stored exactly as each event reported them, and linked, never merged into one record. When two reports of the same thing disagree, both are kept and flagged, rather than one quietly winning. A Model Execution comes only from dbt's run results, never from an OpenLineage event alone.

What a missing link costs

A missing Identity Link never moves money. A Query Execution without one still gets its share of the Billing Line, because billing scope is accounting, not Evidence (ADR 0023). It just has no Roll-up to a Model Execution or Workload Run. So a broken comment configuration shows up as cost that rolls up to nothing, not as cost given to the wrong model.
