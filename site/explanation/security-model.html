    Security model

    On this page

    • Loopback by default
    • One bearer token
    • Bounded payloads
    • Errors never echo input
    • Only the necessary metadata is kept
    • Anonymized samples

    data-finops reads bills and workload metadata, which can show much about a business. This page explains how it limits who can reach it, what it accepts and what it keeps. The decisions are in ADR 0012 and ADR 0024. The threat model is in spec 05. Spec 04 tells what is kept, and spec 06 gives the errors of the API. These documents stay authoritative.

    Loopback by default

    By default, serve binds to 127.0.0.1. Then only the same machine can reach it, and a token is optional. It refuses to bind to a different address without a token. Only a literal loopback address counts: the system resolves a name such as localhost, and that name can point to any address. demo always serves on loopback with no token, so you can try data-finops without a secret.

    One bearer token

    If a token is configured, each route requires Authorization: Bearer <token>, also the dashboard and the API documentation. The HTTP transport of OpenLineage sends this header for its API key. A request with no token or with a wrong token gets 401. The comparison takes constant time.

    • The token comes from DATA_FINOPS_TOKEN or a token file, never both.
    • It must be at least 16 characters, without the spaces at its start and end.
    • It is never logged, printed or stored. Errors say what is wrong with it, not what it is.
    • It proves who has permission to send, not what a request is about: a token is never Evidence for an Identity Link.

    The token is for local and self-hosted use. A Deployment in AWS has no token. Its API accepts only IAM-signed requests. Producers write to an Inbox and do not send over HTTP. See Serve with a token and Deployment architecture.

    Bounded payloads

    • One OpenLineage event can be 1 MiB at most. A larger body gets 413 at the cap, before it is read in full or parsed.
    • A compressed body gets 415. Each event is sent uncompressed.
    • Query history files, dbt artifacts and OpenLineage event files are capped at 512 MiB each. A larger file is rejected before it is read.

    Errors never echo input

    Every API error is an RFC 9457 Problem Details document. It names what was wrong, such as the field that failed validation, but never repeats the value sent. On the command line, a rejected item is named by its position and the reason, never by its content. A secret or a fragment of SQL in a bad input therefore never reaches a log or a terminal through an error.

    Only the necessary metadata is kept

    • A Query Execution keeps only allowlisted metadata: identity, workgroup, statement type, catalog and database, state, times, error category and type, numeric statistics and engine version. Query text, execution parameters, state change reasons, error messages and unknown fields are dropped.
    • From a Trusted Query Comment, only the dbt invocation and node are kept.
    • Before an OpenLineage event is stored, the query text in its SQL facet and the stack traces in its error facets are removed. SQL quoted inside an error message is not detected. A rejected event is never stored.
    • Query text is kept only after an explicit opt-in. No such opt-in exists today.
    • No SQL literals or credentials are exported by the API or the dashboard.

    A Cost Explanation can show the Billing Line in full, tags and free-text names included, or only the columns the contract declares (ADR 0028). By default, serve shows the full line. With --explanation-detail minimal, it shows the minimal line. By default, a Deployment shows the minimal line. If its explanationDetail setting is full, it shows the full line.

    Anonymized samples

    The real-world sample in fixtures/reference-workload/ was anonymized before it was committed. Values were replaced with keyed pseudonyms, account IDs were replaced, and SQL was cut down. The scripts and their secret are described in Exit codes and environment.
