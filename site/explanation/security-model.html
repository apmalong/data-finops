Security model

data-finops reads bills and workload metadata, which can reveal a lot about a business. This page explains how it limits who can reach it, what it accepts and what it keeps. The decisions are in ADR 0012 and ADR 0024, with the threat model in spec 05. They stay authoritative.

Loopback by default

serve binds to 127.0.0.1 unless told otherwise, so only the same machine can reach it, and there a token is optional. It refuses to bind to any other address without a token. Only a literal loopback address counts: a name such as localhost is resolved by the system and could point anywhere. demo always serves on loopback with no token, so trying data-finops needs no secret.

One bearer token

With a token configured, every route needs Authorization: Bearer <token>, the dashboard and the API documentation included. That is the header OpenLineage's HTTP transport sends for its API key. A missing or wrong token gets 401, and the comparison takes constant time.

  • The token comes from DATA_FINOPS_TOKEN or a token file, never both.
  • It must be at least 16 characters, not counting surrounding spaces.
  • It is never logged, printed or stored. Errors say what is wrong with it, not what it is.
  • It proves who may send, not what a request is about: a token is never Evidence for an Identity Link.

Production ingress, such as a private API behind cloud IAM, is a deployment decision still to come. See Serve with a token.

Bounded payloads

  • One OpenLineage event may be at most 1 MiB. A larger body gets 413 at the cap, before it is read in full or parsed.
  • A compressed body gets 415. Each event is sent uncompressed.
  • Query history files and dbt artifacts are capped at 512 MiB each.

Errors never echo input

Every API error is an RFC 9457 Problem Details document. It names what was wrong, such as the field that failed validation, but never repeats the value sent. On the command line, a rejected item is named by its position and the reason, never by its content. A secret or a fragment of SQL in a bad input therefore never reaches a log or a terminal through an error.

Only the metadata needed is kept

  • A Query Execution keeps only allowlisted metadata: identity, workgroup, statement type, catalog and database, state, times, error category and type, numeric statistics and engine version. Query text, execution parameters, state change reasons, error messages and unknown fields are dropped.
  • From a Trusted Query Comment, only the dbt invocation and node are kept.
  • OpenLineage's SQL and stack trace facets are removed before an event is stored, and a rejected event is never stored.
  • Keeping query text would be an explicit opt-in. Nothing does it today.
  • No SQL literals or credentials are exported by the API or the dashboard.

One known exception: a Cost Explanation shows the Billing Line exactly as exported, its tags included. A production deployment must revisit what it exposes there.

Anonymized samples

The real-world sample in fixtures/reference-workload/ was anonymized before it was committed. Values were replaced with keyed pseudonyms, account IDs were replaced, and SQL was cut down. The scripts and their secret are described in Exit codes and environment.
